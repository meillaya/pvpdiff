# Limits and non-goals

`pvpdiff` is advisory. This file lists what it cannot do and why, so a clean
report is not mistaken for a compatibility guarantee.

## Data limits (Hackage mode)

- **Hoogle `.txt` is a lossy rendering.** It records exported declarations and
  instances, not source semantics. It has no roles, deriving clauses, family
  equations/instances, default-method bodies, import graph, or Haddock/GHC
  version. See [feasibility](feasibility.md) §3.
- **Wholesale `module X` re-exports are dropped.** A re-export-only module can
  have zero entries, so adding/removing a whole-module re-export is invisible.
  Named per-name re-exports are duplicated and therefore visible.
- **Class methods are not marked.** "Method added" is heuristic; an ordinary
  method with a default implementation is indistinguishable from one without.
  The rule is `unknown`.
- **Instances are noisy.** GHC/base moves and doc-build differences create false
  removals. Instance removals are `unknown` by default, and `--strict` is not a
  proof either.
- **Behaviour-only changes are invisible.** Functions with identical signatures
  may break users (e.g. changed overflow, exception, or normalization behavior).
  These are the PVP's semantic-compatibility problem; no docs diff can see them.
- **Instances for external types** are generally not in the package's database;
  aeson's added `URI`/`Down` instances and removed attoparsec instances were
  invisible in the go/no-go.
- **Undocumented deprecations** are invisible; only `-- | <i>Deprecated:</i>`
  doc blocks are detected.
- **No proof of compliance.** The classifier can flag a violation candidate; it
  cannot certify that a minor release is compatible.

## Coverage limits

- Both latest and previous Hoogle docs exist for **54/74 (73%)** of random
  packages; 78% have latest docs, 90% of LTS-pinned versions do. Missing docs
  produce `unknown`, not an error. Local mode covers unpublished code and some
  of the gap, but requires GHC/cabal.
- Old docs may use different Haddock conventions (unqualified instances, no
  `[field]` brackets, no class `where {}` blocks). The tool infers era and may
  downgrade to `unknown`; it has no version stamp to rely on.
- Hackage docs may be built with a different GHC/base than the consumer's
  compiler; instance sets can differ for reasons unrelated to the package.

## Local mode limits

- Requires `cabal` and a GHC that can build the package; dependency solving is
  the user's environment, not pvpdiff's.
- v1 supports the main public library. Multi-library packages get a diagnostic
  and may be partially compared until support is added.
- Local docs generated by a different GHC than the Hackage baseline can trigger
  renderer-drift `unknown`s.

## Parsing limits

- The Cabal adapter uses `cabalist-parser` plus local gap fixes. Very old or
  malformed Cabal files may be `unknown`; unparseable files are skipped with a
  counted diagnostic rather than guessed.
- The Haskell type normalizer handles a pragmatic subset. Unsupported syntax
  yields `unknown` comparisons, not panics.
- Conditional APIs weaken the version↔API contract; when Cabal conditionals
  guard the module surface, the module surface is marked `unknown`.

## Product non-goals

- No compilation, test running, or semantic/behavior verification.
- No `.hie`/GHC-API indexing in Hackage mode.
- No source parsing or Haddock HTML scraping in the MVP.
- No role/kind/family-equation/default-method inference from absence.
- No automatic version bumping, publishing, or Hackage enforcement.
- No Stackage solving; snapshots are only a later filter/report.
- No claim that `consistent` means PVP-compliant.

## Security and privacy

- Hackage mode reads public data only, with a descriptive User-Agent and a
  local cache; no credentials.
- Local mode executes `cabal haddock`, which runs the package's build setup and
  can execute `Setup.hs`/build hooks. Treat it like any local build; it is not a
  sandbox.
- The SARIF file contains package names and API names, no source contents.
