# Integration

**Status:** design; the Action ships in P2, blast radius in P3, the survey and
outreach in P4.

## 1. GitHub Action

The primary adoption path is a composite action at the repository root. It
installs a prebuilt `pvpdiff` binary from the matching GitHub Release, runs
`pvpdiff check --package-dir . --against latest`, and writes JSON + SARIF files.
It does **not** upload SARIF itself: the caller owns GitHub permissions and the
upload step, which keeps fork-PR and code-scanning behavior explicit.

Sketch (the implemented version lands in P2):

```yaml
name: PVP API diff

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read
  security-events: write   # required by upload-sarif

jobs:
  pvpdiff:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v7

      - uses: haskell-actions/setup@v2
        with:
          ghc-version: "9.10"
          cabal-version: "3.14"

      - uses: meillaya/pvpdiff@v1
        with:
          package-dir: .
          against: latest
          sarif-file: pvpdiff.sarif
          json-file: pvpdiff.json

      - uses: github/codeql-action/upload-sarif@v4
        continue-on-error: true
        with:
          sarif_file: pvpdiff.sarif
          category: pvpdiff
```

Notes:

- Findings are advisory: `pvpdiff` exits 0 unless `fail-on` is set. SARIF upload
  itself does not fail a workflow on findings.
- Set `fail-on: breaking` (opt-in) for a branch-protection gate. Exit code 100 is
  the gate signal.
- Fork PRs have a read-only token and cannot upload SARIF. Run the analysis on
  `push`/`schedule` or accept a JSON/Markdown artifact for fork PRs; document the
  limitation.
- Pin the action ref and the pvpdiff `version` input together. The release
  workflow is generated by cargo-dist; do not hand-edit it.
- The example Haskell setup action/version is verified in P2; repositories can
  provide GHC/cabal themselves instead.

## 2. Hackage advisory positioning

PVP is a community policy, not enforced by Hackage. The realistic sequence is:

1. Action, SARIF, and a published dataset: self-serve, no gatekeepers.
2. pvp.haskell.org tools entry: only after a track record. The old Tools
   section was removed rather than updated because entries were dead
   ([pvp#47](https://github.com/haskell/pvp/issues/47)).
3. cabal CI signal: comment on the open informational API-diff proposal
   ([cabal#12363](https://github.com/haskell/cabal/pull/12363)); offer classified
   output as a later enhancement.
4. Hackage candidate-page advisory: a non-gating PVP status line would
   require server work and maintainer buy-in. Route it through
   [hackage-trustees](https://github.com/haskell-infra/hackage-trustees) and
   hackage-server, explicitly marking it optional/advisory. Do not propose
   enforcement; Hackage has deliberately kept PVP optional.

## 3. Reverse-dependency blast radius

`01-index.tar.gz` is the only bulk source with dependency bounds. The reverse
page (`/package/<pkg>/reverse`) lists 5,130 dependents for text but shows no
bounds, so it cannot answer "whose range excludes the new version". Sync the
index explicitly and keep it cached; do not scan it per invocation.

Stackage snapshots pin versions, not dependents' bounds. Joining a snapshot's
`cabal.config` with the scanned index data answers "which snapshot packages
would exclude the new version"; it is a P3/P4 filter, not a v1 dependency.
Stackage exposes no machine-readable build-report API, so do not scrape it.

## 4. Data hygiene and rate limits

- Cache immutable Hoogle `.txt` and package tarballs forever; revalidate mutable
  `.cabal` files.
- Descriptive `User-Agent`, ≤2 req/s by default, exponential backoff on
  429/5xx respecting `Retry-After`.
- The index sync is a single conditional GET of ~141 MB; warm runs should be
  304/no-op.
- The survey is opt-in, resumable, rate-limited, and publishes only derived
  data + methodology, not re-hosted package documentation.

## 5. What not to integrate

- No Hackage enforcement or upload gating in the MVP.
- No automatic version bumping or publishing.
- No Stackage solver or build-report scraper.
- No re-hosting of Hackage docs; the report records URLs and hashes instead.
